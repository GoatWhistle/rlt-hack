# Repository Guidelines

## Источники требований и планов

- `task/` — основное ТЗ и входные данные задачи. При расхождении с обсуждениями опирайся на актуальное ТЗ; не изменяй исходные данные без явной необходимости.
- `context/` — сохранённый контекст обсуждений, решения и уточнения. Перед работой по задаче прочитай относящиеся к ней файлы.
- `plans/` — планы реализации и список задач. Поддерживай план в актуальном состоянии по мере выполнения работы.
- `README.md` — краткая инструкция для запуска проекта. Новые команды и требования к окружению документируй здесь.

Если `context/` или `plans/` ещё нет, создай нужный файл при появлении соответствующего материала. Не создавай пустые директории заранее.

## Структура решения

Размещай код по компонентам в корне: `frontend/`, `backend/`, `ml/` и другие каталоги только при необходимости. Тесты держи рядом с соответствующим компонентом по принятой в нём конвенции. В `deploy/` размещай конфигурацию и скрипты развёртывания. Корневой `docker-compose.yml` должен поднимать все сервисы, необходимые для локального запуска решения; инструкции и переменные окружения опиши в `README.md`. Не складывай исходный код в `deploy/`.

## Backend

### Архитектура

Весь код backend лежит в `backend/src` и разделён по слоям:

- `adapter/` — реализация адаптеров исходящих внешних запросов:
  - `adapter/repository/` — базы данных;
  - `adapter/client/` — внешние сервисы;
  - `adapter/broker/` — брокеры сообщений.
- `service/` — вся бизнес-логика. Слой не знает о внешней инфраструктуре: не импортирует адаптеры, драйверы БД, HTTP-клиенты и SDK брокеров, а работает только через интерфейсы.
- `controller/` — приём входящих запросов. Вызывает функции `service` только через слой абстракции, бизнес-логику в себе не держит.
- `models/` — только бизнес-модели: сущности предметной области, с которыми работает `service`.

Модели, относящиеся к `controller/` и `adapter/` (схемы запросов и ответов, строки БД, payload брокера, форматы внешних API), в `models/` не держи — объявляй их как DTO по месту использования, рядом с потребляющим кодом.

### Оформление кода

- Абсолютно все интерфейсы объявляй по месту использования — в файле `protocols.py` рядом с кодом, который этот интерфейс потребляет.
- Ошибки объявляй на уровне папки слоя: `adapter/repository/errors.py`, `service/errors.py` и так далее.
- Импорты пиши только в начале файла. Импорты внутри функций и методов запрещены.
- Весь код пиши асинхронным: функции слоёв объявляй через `async def`, используй асинхронные драйверы и клиенты. Синхронные блокирующие вызовы в асинхронном коде запрещены — при необходимости выноси их в пул потоков.
- Разделяй код по папкам: на каждую логическую часть слоя — своя папка (например, `adapter/repository/clickhouse/`, `service/parsing/`, `controller/job/`), а не один большой модуль.

## Frontend

Стек: React 19, TypeScript, Vite, React Router, TanStack Query, i18next, CSS Modules. Линтер и форматтер — Biome (`biome.json` в корне), тесты — Vitest + Testing Library, e2e — Playwright + axe.

### Слои

Код лежит в `frontend/src`, слои импортируют только вниз: `app → pages → features → entities → shared`.

- `app/` — сборка приложения: провайдеры, роутер, оболочка, корневой error boundary.
- `pages/` — страницы маршрутов, по папке на страницу.
- `features/` — пользовательские действия (переключатель языка и т. п.).
- `entities/` — доменные сущности и их запросы; создаётся, когда появится первая сущность.
- `shared/` — переиспользуемое без знания домена: `api/`, `config/`, `errors/`, `i18n/`, `motion/`, `styles/`, `ui/`.

Пакеты называй по содержимому: папки `utils`, `helpers`, `common`, `lib`, `core`, `misc` запрещены, `shared` — только `src/shared`.

### Правила кода

- Никаких комментариев: ни в коде, ни в CSS, ни в HTML. Единственное исключение — `// biome-ignore <правило>: <причина>`.
- Файл не длиннее 250 строк, в папке не больше 20 исходников и 30 тестов.
- Импорты только в начале файла, только именованные экспорты (кроме конфигов инструментов).
- Весь пользовательский текст — в JSON-словарях `src/shared/i18n/locales/{ru,en}/*.json`. Кириллица в коде и литеральный текст в JSX запрещены. Ключи `t()` типизированы по английскому словарю, наборы ключей ru и en совпадают.

### Стили

- У компонента со стилями своя папка: `index.tsx` + `styles.module.css`. Лист импортирует только его компонент, классы читаются как `styles.name`, неиспользуемые классы запрещены.
- Глобальные стили только в `src/shared/styles/` (`global.css`, `reset.css`, `tokens/*.css`), подключаются один раз в `main.tsx`.
- Цвета, длительности, кривые и `!important` — только в `src/shared/styles/tokens/`. В остальных местах — `var(--token)`.
- Одинаковые блоки деклараций (от трёх свойств) в разных местах запрещены: переиспользуй компонент или вынеси токен.
- Анимации входа и выхода: токены `--motion-*` из `tokens/motion.css`, хук `usePresence` и компонент `Transition`. При `prefers-reduced-motion` длительности сводятся к 1 мс.
- Визуальная система описана в `frontend/DESIGN.md` («Ясный атлас»), её значения лежат в `src/shared/styles/tokens/`. Скиллы `impeccable` и `ui-ux-pro-max` применяй в рамках этих правил.

### Ошибки

- Ответы API превращаются в `ApiError` (`status`, `code`). Текст для пользователя берётся из словаря `errors` по коду, иначе по статусу (`describeError`).
- Корневой `AppErrorBoundary` ловит падения рендера, `RouteErrorPage` разделяет 404, устаревший чанк после деплоя и прочие ошибки маршрута, `ErrorState` используется для ошибок внутри страниц.
- Ошибки мутаций автоматически показываются тостом; чтобы отключить, передай `meta: { silent: true }`.

### Проверки

Перед сдачей в `frontend/` должен проходить `npm run verify`: правила репозитория, типы, Biome и тесты с покрытием не ниже 80 % по строкам, веткам, функциям и выражениям. Правила проверяет `scripts/checks/` (`npm run rules`); у каждого правила есть тест на нарушение и на чистый код, а `tests/checks/repository.test.ts` прогоняет их по всему репозиторию. Тесты лежат в `frontend/tests/` и повторяют структуру `src/`, e2e — в `frontend/e2e/`.

## Разработка и проверка

Сейчас в репозитории нет настроенных команд сборки, тестирования и форматирования. При добавлении компонента зафиксируй его зависимости и команды запуска в конфигурации компонента, а в `README.md` укажи команды сборки, тестов и запуска через Docker Compose. Перед сдачей изменений запусти относящиеся к ним проверки. Соблюдай стиль выбранного языка и используй настроенный форматтер или линтер; называй файлы и сущности по их назначению.

## Общение и инструменты

Отвечай на русском языке кратко, чётко и понятно, без лишних вступлений. Если запрос подразумевает доступный MCP, skill или другой специализированный инструмент, используй его сразу по назначению. Сначала сверяйся с относящимися к задаче материалами из `task/`, `context/` и `plans/`.

## Git и pull request

Пиши короткие, понятные названия и описания коммитов по сути изменения, например `Добавить загрузку данных`. Не добавляй `Co-authored-by` для агентов, упоминания ИИ или другие следы участия агентов в коммиты, код и PR. В PR кратко укажи, что изменилось и как это проверено; приложи скриншоты при изменении интерфейса.

По указанию владельца рабочей копии делай коммиты и push завершённых, проверенных изменений от его Git-идентичности: `andreysk0304 <andreysk0304@yandex.ru>`. Используй локальную конфигурацию репозитория; не меняй глобальную. Перед push обновляй origin и сохраняй чужие изменения. Не используй force push.

## Данные и обучение

- Перед ML-работой читай `task/ML_SPEC.md`, `context/decisions.md`, `context/hardware.md`, `context/organizers.md` и актуальный план в `plans/`.
- Датасет обрабатывай только на сервере, исходный архив находится в `/root/rlt`. Локальные тесты используют только искусственные данные. Не скачивай CSV из LFS на рабочий компьютер.
- Исходный архив и README сервера не изменяй. Производные файлы, окружения и веса храни вне Git; в репозиторий добавляй код, конфигурацию и агрегированные отчёты.
- Пароли, токены и SSH-ключи не сохраняй в репозитории. Настройка доступа не является частью контекста задачи.
- Модели во время обучения и применения загружай из локального кеша. Внешние LLM API в решение не добавляй. Отдельная загрузка открытых весов относится к подготовке окружения.
- Подготовка и CPU-проверки выполняются на существующем сервере. Для энкодера рассматривается аренда RTX 5060 Ti с 15 ГБ доступной VRAM за 22 ₽/час; точный прогон начинается после предоставления доступа к GPU.
- На всём протяжении работы веди `ml/EXPERIMENTS.md`: перед экспериментом запиши гипотезу и конфигурацию, после — измеренные метрики, время, память, выборку, артефакты и вывод. Указывай статус и ограничения. Технический smoke-test не выдавай за оценку качества; не придумывай отсутствующие измерения.
