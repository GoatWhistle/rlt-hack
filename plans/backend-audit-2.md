## Резюме

На объёме `bench` по умолчанию (300 тыс. карточек, 100 тыс. лотов) поиск укладывается в бюджет: p50 282 мс, p95 437 мс последовательно. Но при числе строк как в реальном датасете закупок (604 тыс. извещений, 2,97 млн позиций ТРУ, 1,2 млн участий) и ограничении ClickHouse как в продакшне (`cpus: 2`, 1,5 ГБ) картина другая:

- поиск по одной позиции идёт 2,1 с, по пяти — 6,7 с, по десяти и больше — всегда 504;
- при четырёх одновременных пользователях половина поисков заканчивается 504;
- без ограничения CPU (16 ядер) запрос на 25 и 50 позиций тоже даёт 504 и на всё время выполнения отнимает пул у остальных: короткий поиск рядом с ним тоже получает 504.

Причины:

- Каждая позиция порождает два полных прохода. Лексический канал читает все `offers` через `FINAL`, канал истории — все `procurement_lots`, `procurement_items` и `lot_participations`. Это 4,78 млн строк на позицию.
- Индексы `tokenbf_v1` и `ngrambf_v1` не отсекают ни одной гранулы ни в одном из 72 запросов замера.
- В процессе API на каждую позицию анализируются 500 текстов. Поиск на 50 позиций — это 2,6 с чистого CPU Python в единственном процессе.

Схема данных в порядке. Полная цепочка миграций проходит и с нуля, и со старой нумерацией ветки. Представления `*_current` после `0007` содержат все колонки нормализации, порядок колонок совпадает с таблицей, `withdraw_absent` (`INSERT … SELECT *`) работает с новой колонкой `search_text`. Слабые места данных:

- нет TTL у архива поисков и загрузок;
- проверка незавершённых закупок каждые 60 с читает всю историю загрузок;
- `0007` пересоздаёт представление неатомарно;
- исторические миграции нельзя переприменить после `0006`.

Находок: **P0 — 1, P1 — 5, P2 — 11**.

## Находки

### P0 — блокирует релиз

#### 1. На реальном объёме закупок поиск не укладывается в 8 с

- Статус: **закрыто**. Канал истории читает `lot_texts` (строка на лот: нормализованный текст предмета, названия и позиций, участники, победители), сводка участий — `supplier_lots` (строка на пару поставщик–лот, ключ `(supplier_id, lot_id)`). Обе таблицы и `offers` получили текстовый индекс по префиксам слов (находка 3), флаги совпадений терминов читаются из индекса. Таблицы собирает обновляемое представление `REFRESH EVERY 1 DAY` (миграция `0014`); после загрузки истории их обновляет `SYSTEM REFRESH VIEW` (`backend/README.md`). Повторный замер серии D (`ml/EXPERIMENTS.md`, `PERF-001`): 1 позиция — p95 2,8 → 1,2 с; 5 — 3 из 7 ответов 504 → p95 1,6 с; 10 — все 504 → p95 3,2 с; 25 и 50 (обрезаются до 20) — все 504 → p95 4,1–4,4 с; 4 одновременных — 40 из 40 ответов 504 → 0, p95 4,3 с; 8 одновременных — 80 из 80 → 5 из 80. С `CLICKHOUSE_MAX_THREADS=2` (теперь в `production.env.example`) 4 одновременных — p95 2,5 с и 2,0 поиска в секунду, 8 одновременных — 2 ответа 504 из 80. Критерий «p95 ≤ 3 с для 1–3 позиций, 0 ответов 504 при 4 одновременных» выполнен. Остаток — чтение карточек для обогащения (находка 7): ≈0,7 из 1,3 с CPU ClickHouse на поиск. Тесты: `tests/adapter/repository/test_search_index.py`, `test_search_adapters.py`, `test_relevance_cost.py`, `tests/service/supplier_search/test_search_budget.py`.

- Где:
  - `backend/src/adapter/repository/clickhouse/offer_search/retriever.py:84-95` и `history_search/retriever.py:81-100` — по одному SQL на позицию в каждом канале, `asyncio.gather` по всем позициям;
  - `offer_search/query.py:7-16` — полный проход `offers_current` (`FINAL`), сортировка по `multiSearchAllPositions`;
  - `history_search/query.py:3-22` — `UNION ALL` по `procurement_lots_current` и `procurement_items_current` с вычисляемым `replaceAll(lowerUTF8(...))`, `GROUP BY lot_id`, затем соединение со всеми `lot_participations_current`;
  - `participation/query.py:3-15` — три представления с `FINAL` на каждый поиск;
  - `adapter/text/rule_interpreter/interpreter.py:14` — `MAX_ITEMS = 50`;
  - `deploy/compose.production.yml:35-36` — у ClickHouse `cpus: 2`, а `production.env.example` задаёт 1500m. При этом `CLICKHOUSE_POOL_SIZE=4` × `CLICKHOUSE_MAX_THREADS=4` — это 16 потоков на 2 ядра.
- Воспроизведение (раздел «Замеры», серии C и D):
  - `seed_scale.py` наполняет `rlt-audit2` синтетикой: 1 млн карточек, 604 452 лота, 2 971 651 позиция ТРУ, 1,2 млн участий. Затем ClickHouse ограничивается `docker update --cpus 2 --memory 1500m`.
  - `bench.run --sequential 30 --concurrency 4 --requests 40`: последовательно p50 **2,24 с**, p95 **3,41 с**; при четырёх одновременных — **20 из 40 ответов 504**, 0,5 RPS.
  - `big_query2.py`: 1 позиция — 2,1 с, 3 — 4,4 с, 5 — 6,7 с, 10 — **504**.
  - Даже на 16 ядрах (серия C): 10 позиций — 4,1 с, 25 и 50 — **504**.
  - Самая дорогая стадия — канал истории: 1,76 с p50 на одну позицию при 2 CPU, 4,78 млн прочитанных строк.
- Исправление:
  - Канал истории — на заранее собранную таблицу текстов лотов, одна строка на лот (`lot_id`, нормализованный текст предмета и позиций). Строится при загрузке истории или командой `main.py`. Замер G: 439 → **166 мс**, в 2,6 раза быстрее, чтение 4,78 → 1,81 млн строк. Следующий шаг — хранить в ней и участников лота, тогда соединение с `lot_participations` уходит.
  - Индекс, который реально отсекает данные: находка 3.
  - Справедливая доля пула на один поиск и предел позиций интерактивного поиска: находка 2.
  - Конфигурация продакшна: `CLICKHOUSE_MAX_THREADS=1–2` при `cpus: 2` либо больше ядер для ClickHouse. Решение принять по повторному замеру D.
  - Простое объединение позиций в один SQL **не помогает**. Замер H: один проход по 1 млн строк с 25 выражениями `multiSearchAllPositions` занимает 3,6 с против 1,8 с у 25 отдельных запросов через 4 слота. Стоимость здесь в подсчёте совпадений, а не в чтении.
- Тест:
  - Приёмочный замер `bench` с пресетом объёма реального датасета и ClickHouse `cpus: 2`. Критерий: p95 ≤ 3 с для запросов из 1–3 позиций, 0 ответов 504 при четырёх одновременных. Результат записать в `ml/EXPERIMENTS.md` как технический замер.
  - `tests/service/supplier_search/test_query_budget.py::test_sql_per_search_is_bounded` — фейковый шлюз считает запросы: их число на поиск ограничено константой или долей пула и не растёт линейно с числом позиций сверх предела.

#### 2. Один большой поиск занимает весь пул и вытесняет остальных

#### 3. Индексы `tokenbf_v1` и `ngrambf_v1` не отсекают данные

- Статус: **закрыто**. Миграция `0013` удаляет оба блум-фильтра и строит `INDEX … TYPE text(tokenizer = array)` по массиву префиксов слов `search_text` длиной 3–6 символов. Запрос ищет термины запроса через `hasAnyTokens` по тому же выражению, ClickHouse читает флаги из индекса. `EXPLAIN indexes = 1`: отсутствующее слово — 0 гранул. На 1 млн карточек лексический запрос читает 52 МиБ вместо 284 МиБ и тратит 0,12 с CPU ClickHouse вместо 0,65 с. Тесты: `tests/adapter/repository/test_search_index.py` (chDB), `test_migration_contract.py` (выражение индекса совпадает с выражением запроса).

- Где: `backend/migration/0007_offer_search_index.sql:6-10,15-17`; `retrieval/terms.py:10-12,118-120` (`MIN_NEEDLE_LENGTH = 3`, иглы — общий префикс токена и стема); `offer_search/query.py:11`.
- Воспроизведение (`explain_lexical.sql`, `explain3.sql`, объём `bench`: 37 гранул, `GRANULARITY 4` — около 10 блоков по 32 768 строк):
  - `tokenbf_v1` не участвует в `multiSearchAny` по префиксам. Для отсутствующего слова `зщзщзщ` он оставляет 37 из 37 гранул; срабатывает только на `hasToken`. Это ≈312 КиБ на 300 тыс. строк и работа при каждой вставке и мутации без пользы.
  - `ngrambf_v1(4, …)` срабатывает, только если все иглы длиннее 3 символов и ни одна не встречается в блоке. Достаточно одной трёхбуквенной иглы (`мыл`, `рис`, `шин`, `син`, `120`, `e27` — 17 из 72 наборов игл в `bench`), и `['зщзщзщ', 'щзщ']` читает все 37 гранул.
  - Частые слова есть в каждом блоке из 32 тыс. строк: порядок `ORDER BY offer_id` (uuid5) случайный относительно текста.
  - Итог: во всех запросах замера `read_rows` равно размеру таблицы — 300 000 или 1 000 000.
- Исправление:
  - Удалить `idx_offers_search_tokens` новой миграцией либо перейти на колонку стемов и `hasAnyTokens`/`hasToken`.
  - Рабочий вариант для префиксного поиска: колонка `search_stems` со стемами `RussianAnalyzer`, которую пишет адаптер при сохранении карточки, и текстовый (инвертированный) индекс ClickHouse по ней. Поиск по стемам через `hasAnyTokens` использует индекс, а не полный проход.
  - Пока ngram остаётся — `GRANULARITY 1` и иглы не короче 4 символов в фильтре `WHERE`. Короткие иглы оставить только в оценке.
- Тест: `tests/clickhouse/test_offer_search_index.py` (Linux, chDB). `EXPLAIN indexes = 1` для иглы, которой нет в данных, — 0 выбранных гранул. Для набора с трёхбуквенной иглой фильтр `WHERE` строится только из игл длиной от 4 символов.

## Что уже хорошо

- **Исправления первого аудита работают и не замедляют поиск.**
  - После 504 запросы в ClickHouse отменяются: 22 запроса с кодом 394 (`QUERY_WAS_CANCELLED`) в среднем через 372 мс после отмены, 26 вызовов `KILL QUERY … ASYNC`, слоты освобождаются.
  - `max_execution_time` = 10 с для интерактивного пула больше реальных запросов, лишних обрывов нет.
  - Раздельные фоновый и интерактивный пулы и управляющий клиент не добавляют задержки.
  - Единственный побочный эффект — таймаут архива (находка 6).
- **Миграции.** Мигратор применяет файлы по имени и проверяет контрольную сумму. Оба файла `0004_*` идут в верном порядке. `0007`–`0009` идемпотентны (`IF NOT EXISTS`). Представления после полной цепочки не теряют колонок нормализации `0004`/`0005` и переименований `0006`.
- **`search_text`** вычисляется `DEFAULT`-выражением при вставке. Писатель карточек его не передаёт, поэтому новые версии строк всегда согласованы с названием и описанием. Нормализация `ё`/регистра в SQL и в анализаторе совпадает.
- **`ReplacingMergeTree` и версии.** Версия `searches`, `uploads`, `upload_lots`, `upload_results` — микросекунды времени события. Повтор той же записи не создаёт новой версии. Чтение по `search_id` и `upload_id` идёт по первичному ключу. `recent` на миллионе поисков — 45 мс.
- **Идентичность.** `supplier_id` — uuid5 от нормализованного ИНН, поэтому одна компания с ИНН — одна запись. `ids_by_inn` отбрасывает ИНН с двумя записями вместо случайного выбора. Сводка участий группирует по `(supplier_id, lot_id)` и не размножает участие при соединении с многопозиционными лотами (`task/ML_SPEC.md`).
- **Сжатие.** `payload` с `ZSTD(3)` сжимается в 15,8 раза. Ответ поиска 25–97 КБ сжимается gzip в 9–11 раз; gzip включён в nginx, zstd/gzip — в Caddy.
- **Асинхронность.** Сопоставление и BM25 вынесены в `to_thread`, стемы кэшируются (`lru_cache` на 200 тыс.), запросы каналов и обогащения идут параллельно.
- **Замер есть.** `bench/` наполняет данные `INSERT … SELECT` за секунды (1 млн карточек — 11 с) и даёт разбивку по стадиям из `query_log`. На нём эти находки и воспроизведены.
