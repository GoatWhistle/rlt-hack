# Аудит совместимости после слияния поиска поставщиков

Проверка 2 октября 2026 года, `main` на коммите `37dc414`. Ветка
`feature/supplier-search-api` слита и отправлена в `origin/main`.
Сценарий загрузки CSV пока нельзя считать рабочим: ответ backend несовместим
с парсером фронтенда, а стандартный запуск не включает обслуживающий его сервис.

## Что изменилось

- Добавлены API поиска, архив результатов, профили поставщиков и интерфейс поиска.
- Удалён демонстрационный режим фронтенда, добавлены выбор кандидата и экспорт.
- Появились ограничения запросов, диагностика ошибок, проверки доступности БД.
- После слияния сохранены два конвейера: `/api/searches` обслуживает `api`,
  а `/api/uploads` и `/api/suppliers/search` — отдельный `search-api`.
  Последний использует подготовленный индекс и энкодер. Наличие обученного
  ранжировщика в нём не означает, что этот ранжировщик используется обычным поиском.
- Часть улучшений CSV и экрана закупки не перенесена при слиянии;
  перечень есть в [paused-work.md](paused-work.md).

## Подтверждённые проблемы

### P0 Ответ загрузки не принимается фронтендом

`backend/src/controller/uploads/presentation.py:39` не возвращает `counts.failed`.
`frontend/src/entities/upload/parse.ts:62` требует это поле числом.
Проблема затрагивает создание загрузки, непустой список загрузок и детали закупки.

Воспроизведение: создан искусственный `Upload` с одним лотом, его ответ получен
настоящей функцией `summary()` и передан настоящей `parseUploadSummary()` через
Vite и Chromium. Результат: `PayloadFormatError: unexpected payload at $.counts.failed`.
Для воспроизведения не использовались исходные CSV организаторов.

- [ ] Согласовать полный ответ загрузки и проверить его парсером фронтенда.
- [ ] Добавить проверку совместимости реальных сериализаторов обеих сторон.

### P0 Стандартный Compose не запускает API загрузок

`docker-compose.yml:24` включает `search-api` только в профиле `search`, а зависимость
фронтенда от него необязательная. `deploy/nginx.conf:66` отправляет все загрузки
именно в этот сервис. `docker compose config --services` без профиля показывает
`clickhouse`, `clickhouse-ui`, `migrate`, `api`, `frontend`, без `search-api`.
Следовательно, после стандартного запуска обработчик загрузок недоступен.
После успешной пересборки `GET /api/uploads` через `localhost:8080` вернул
`502 text/html`; основной `/api/health/ready` одновременно вернул `200` и
подтвердил доступность ClickHouse. Ошибка подтверждена по HTTP.

В релизе `deploy/release.sh:112` поднимает только `api frontend` с `--no-deps`.
Запуск `search-api` выполняется отдельно через `start_workers` и
`deploy/run-workers.sh`, только при включении `RLT_RUN_WORKERS=true` и
`RLT_RUN_SEARCH=true`. Без этих флагов свежий релиз также не поднимает API загрузок.

Для отдельного сервиса также нужен подготовленный индекс. Локального каталога
`data/supplier-index` при проверке нет. Одного включения профиля недостаточно
для запуска ML-конвейера без его артефактов и энкодера.

- [ ] Определить обязательные сервисы полного сценария и согласовать Compose,
  nginx, инструкцию запуска и проверку готовности.
- [ ] Проверить загрузку через nginx на подготовленном окружении.

### P1 Интерфейс и backend допускают разное количество закупок

`frontend/src/entities/upload/http.ts:12` задаёт 5000 строк,
`backend/src/controller/uploads/csv_file.py:37` и `service/upload/worker.py`
ограничивают файл 20 закупками. Экспорт `SelectedLots` также ограничен 20.
Искусственный CSV с 20 строками принят, с 21 строкой отклонён:
`ValueError: too many rows`. Пользователь проходит предварительную проверку
интерфейса, но получает отказ backend.

- [ ] Согласовать лимиты, текст интерфейса и пакетный экспорт.

### P1 Проверка релиза вызывает отсутствующий маршрут

`deploy/smoke.sh` опрашивает `/api/uploads/{id}/summary`, который отсутствует в
`backend/src/controller/uploads/api.py`. Такой вызов не может завершиться успешно.
Фронтенд тоже содержит этот запрос, но сейчас backend обрабатывает загрузку
целиком до ответа и возвращает `processed == total`, поэтому обычный опрос
прогресса может не включаться. Основной подтверждённый эффект здесь —
несовместимость проверки релиза с текущим API.

- [ ] Согласовать контракт прогресса и smoke-проверку с выбранной обработкой CSV.

## Что проверено

- `npm run verify`: успешно, 349 тестов в 47 файлах; пройдены правила, TypeScript,
  Biome и пороги покрытия. Покрытие строк 97,83%, ветвей 90,77%.
- `npm run e2e`: успешно, 40 тестов для desktop и mobile.
- E2E используют подменённые ответы API (`e2e/api-fixture.ts`,
  `e2e/search-fixture.ts`), поэтому не подтверждают интеграцию с реальным backend.
- Проверка настоящего ответа загрузки парсером фронтенда: ошибка воспроизведена.
- Граница CSV 20/21 строк: несовпадение лимитов воспроизведено.
- Push подтверждён чтением `refs/heads/main` с origin.
- Backend `uv run --frozen ruff check .`: успешно.
- Backend `uv run --frozen mypy`: 6 ошибок `no-untyped-call` в
  `tests/embedding/document_smoke.py`, `tests/clickhouse/offer_batch_smoke.py`,
  `tests/embedding/smoke.py`. Общая проверка типов сейчас не проходит.
- Backend `uv run --frozen --all-extras pytest`: 402 passed, 14 errors, 21,72 с.
  Окружение — macOS, Python 3.14.0. Первая ошибка возникает при подготовке БД:
  установленный chDB не содержит функцию `lowerUTF8`; остальные ошибки связаны
  с уже инициализированным EmbeddedServer после неуспешной подготовки.
  В отдельном процессе `SELECT lowerUTF8('ТЕСТ')` тоже падает без кода приложения.
  В Docker ClickHouse 26.9.7.9 тот же запрос возвращает `тест`.
  Поэтому 14 ошибок нельзя трактовать как 14 подтверждённых дефектов приложения,
  но успешного полного backend-прогона в этом окружении нет.

## Ограничения и дальнейшая проверка

`docker compose up -d --build api frontend` завершился успешно. Миграции
применились, `api`, `frontend` и ClickHouse имеют статус healthy.
Через nginx проверены два запроса к `/api/searches`:

| Запрос | HTTP | Кандидатов | Время одного запроса |
| --- | --- | --- | --- |
| Металлическая кровать | 201 | 20 | 1,87 с |
| Бумага офисная | 201 | 20 | 0,52 с |

Повторное открытие обоих результатов и профилей первых кандидатов вернуло 200.
В Chromium выполнен настоящий поиск «Металлическая кровать» через интерфейс:
открылась страница результата с 20 кандидатами и основаниями, ошибок JavaScript
не было. Ответы API в этой проверке не подменялись. Это проверка работоспособности
двух коротких запросов, а не оценка качества рекомендаций или нагрузочный тест.
В показанных результатах использовался лексический канал.

До пересборки локальный frontend был старым контейнером:
`GET /api/health/ready` возвращал `200 text/html`, а сервисы API не работали.
После пересборки основной health возвращает корректный JSON.

В [backend-audit-2.md](backend-audit-2.md) остаётся открыта проблема таймаутов
поиска на синтетике размера полного архива. Здесь тот нагрузочный эксперимент
не повторялся; его цифры нельзя выдавать за свежие измерения этого коммита.
Качество ML, внешние источники и развёрнутый сервер в этой проверке не переоценивались.

Порядок исправлений: контракт CSV → полный запуск сервисов → лимиты и smoke →
проверка реального сценария через nginx → повторная проверка производительности.
