# План улучшения карточек поставщиков

Дата: 2026-10-01.
Статус: в работе; варианты A–D построены, tokenizer-аудит завершён. Retrieval
ограничен вариантами A (256) и D (512). Локальный A-run отменён до получения
метрик; пользователь предложил Polza API для ускорения. Synthetic smoke-test
подтвердил доступность Qwen3-Embedding-4B, но передача реальных карточек и
validation-запросов провайдеру ожидает явного подтверждения.

## Цель

Проверить, теряется ли полезная товарная информация при ограничении карточки
256 токенами, и выбрать представление поставщика по качеству поиска и стоимости
вычислений. Улучшение качества пока является гипотезой.

Основания: [ML-постановка](../task/ML_SPEC.md),
[принятые решения](../context/decisions.md),
[ресурсы](../context/hardware.md),
[уточнения организаторов](../context/organizers.md),
[общий план](../plans/implementation.md),
[журнал экспериментов](EXPERIMENTS.md).

## Текущее поведение

- `src/rlt_ml/prepare.py` формирует карточки по поставщику и категории ОКПД2.
- В карточку попадают до пяти последних уникальных описаний. Каждое начинается
  с первых 400 символов текста извещения, затем содержит до пяти названий ТРУ.
- Для поставщика сохраняется до восьми карточек направлений деятельности.
- `src/rlt_ml/text_encoder.py` обрезает вход токенизатором до `max_length`;
  в текущем сравнении энкодеров это 256 токенов.
- Точная доля обрезанных карточек и потерянных товарных сведений не измерена.

## 1. Зафиксировать условия сравнения

- [ ] Использовать ту же выборку из 1 000 validation-запросов, seed 42 и историю
  до 2024-12-01, что в завершённых retrieval-экспериментах.
- [ ] Сохранить список `lot_id`, состав доступных поставщиков, хеши исходных
  артефактов, ревизию кода, конфигурацию и ревизию модели.
- [ ] Основное сравнение провести на Qwen3-Embedding-4B. Возможный пилот на 0.6B
  оформить отдельно; результаты разных моделей не смешивать.
- [ ] Разделить лимиты запроса и карточки. Во всех вариантах запрос ограничен
  256 токенами; меняются только представление и лимит карточки.
- [ ] Зафиксировать отдельный BM25-индекс на исходных карточках и одинаковый RRF,
  чтобы первое сравнение показывало эффект изменений в векторном поиске.
- [ ] Перед каждым запуском записать гипотезу и конфигурацию в `EXPERIMENTS.md`.

Тексты и число карточек здесь намеренно меняются. Неизменны доступная история,
набор поставщиков, запросы, модель и остальные параметры поиска. Для каждого
варианта сохраняется собственный хеш карточек.

## 2. Измерить обрезку

- [ ] На сервере загрузить токенизатор выбранной модели из локального кеша
  с зафиксированной ревизией. Для подсчёта токенов загрузка весов модели не нужна.
- [ ] Применить то же форматирование текста и правила специальных токенов,
  что при индексации, затем измерить длину без truncation и padding.
- [ ] Для лимитов 256 и 512 посчитать долю карточек, требующих обрезки,
  p50/p90/p95/p99 длины и долю отброшенных токенов:
  `sum(max(L_i - limit, 0)) / sum(L_i)`.
- [ ] Дополнительно сверить фактический результат обрезки токенизатором,
  учитывая специальные токены. Метрика длины не равна потере полезной информации.
- [ ] Построить срезы по категории, числу примеров в карточке и объёму истории
  поставщика; отдельно показать компании с 1–5 историческими участиями.
- [ ] Просмотреть на сервере 30–50 карточек разных длин и категорий: полный текст,
  сохранённое начало и отброшенный хвост. Включить короткие карточки для сравнения.
- [ ] Для товарных фрагментов восстановить происхождение из исторических ТРУ
  и отметить, какие названия и характеристики полностью или частично обрезаны.
- [ ] Сохранить агрегированный отчёт и вывод: какие сведения теряются и насколько
  распространена проблема. Реальные тексты карточек оставить на сервере.

## 3. Подготовить компактное представление

- [ ] Поставить в начало направление деятельности, конкретные товары/услуги,
  затем значимые характеристики и короткие примеры опыта.
- [ ] Брать сведения только из доступной истории. Не добавлять характеристики,
  роли компании или специализацию без подтверждающих данных.
- [ ] Сократить повторяющиеся служебные формулировки и реквизиты заказчиков.
  Сохранить модели, артикулы, марки, размеры, единицы и технические характеристики.
- [ ] Сохранять исходный текст и связь с подтверждающими лотами отдельно
  от текста, который получает энкодер.
- [ ] Удалять точные и близкие дубли, сохраняя различающиеся характеристики.
- [ ] Отбирать разнообразные товарные примеры внутри направления; зафиксировать
  детерминированный порядок и правило разрешения равенств.
- [ ] Собирать текст с учётом токенов: сначала обязательные сведения,
  затем целые дополнительные фрагменты в пределах оставшегося бюджета.
- [ ] Сохранить состав поставщиков и направлений исходного варианта; при нехватке
  товарных описаний использовать доступный текст закупок.

Пример структуры на искусственных данных:

```text
Направление: компьютерная техника.
Товары: системные блоки; мониторы; оперативная память.
Характеристики: DDR4; мониторы 24 дюйма.
Опыт: поставка компьютерного оборудования.
```

## 4. Сравнить варианты

| Вариант | Представление | Лимит карточки | Что проверяем |
| --- | --- | ---: | --- |
| A | Текущая склейка описаний | 256 | Воспроизведение baseline |
| B | Компактная карточка, товары в начале | 256 | Эффект упаковки относительно A |
| C | Несколько коротких карточек товарных групп внутри направления | 256 | Эффект разделения относительно B |
| D | Текущая склейка описаний | 512 | Эффект длины относительно A |

- [ ] Для C использовать те же исходные факты, что для B. Зафиксировать лимит
  карточек и правила группировки; сообщать фактическое число карточек и векторов.
- [ ] Сохранять агрегацию по уникальному поставщику через максимум сходства.
  Не суммировать баллы карточек; лимит извлекаемых карточек учитывать при изменении
  их максимального числа на поставщика.
- [ ] Сначала воспроизвести A, затем выполнить B, C и D в сопоставимых условиях.
  Измерять время каждого запуска без параллельной нагрузки других экспериментов.
- [ ] Для каждого варианта оценить отдельно векторный поиск и гибрид
  с зафиксированным BM25-индексом.
- [ ] После выбора представления отдельно проверить перестроение BM25
  на новых текстах, чтобы измерить дополнительный эффект лексического канала.

## 5. Оценить результат

- [ ] Посчитать Recall@100 известных участников, Recall@100 исторического
  победителя и MRR победителя на одной выборке.
- [ ] Отдельно показать многопозиционные лоты, малую историю и лоты с новым
  участником. Поставщиков без карточек учитывать в общих знаменателях.
- [ ] Разделить покрытие базы и полноту поиска среди доступных поставщиков.
- [ ] Посчитать парные изменения метрик и доверительные интервалы по одним
  запросам; связанные лоты одной процедуры учитывать совместно при bootstrap.
- [ ] Записать время подготовки карточек и индексации, размер индекса,
  p50/p95 задержки поиска и пики RAM/VRAM.
- [ ] Разобрать примеры улучшения и ухудшения, включая потерю точных обозначений
  и редких направлений после сокращения текста.
- [ ] Выбрать вариант по измеренному качеству и расходу ресурсов. При отсутствии
  убедительного выигрыша сохранить исходный вариант и зафиксировать вывод.

Исторические метрики оценивают восстановление известных участников и победителя.
Они не заменяют экспертную оценку релевантности. Итоговый test используется
после выбора конфигурации, а не для подбора представления карточек.

## 6. Проверки и артефакты

- [ ] Проверить на искусственных данных сохранение артикулов и характеристик,
  удаление дублей, детерминированность отбора и соблюдение токенного бюджета.
- [ ] Проверить отсутствие целевого лота и будущих сведений в карточках,
  сохранение поставщиков и корректную агрегацию нескольких карточек по ИНН.
- [ ] Сохранить на сервере конфигурации, хеши, карточки, векторы, предсказания,
  логи и подробные отчёты; исходный архив и серверный README не изменять.
- [ ] В Git добавить код, конфигурации и агрегированные результаты.
  Дополнить `EXPERIMENTS.md` измерениями, ограничениями и принятым решением.
- [ ] При добавлении команд описать их в корневом README и обновить общий план.

Все операции с датасетом выполняются на серверах. Локальные проверки используют
искусственные данные. Модели и токенизаторы при применении загружаются
из локального кеша; подготовка кеша выполняется отдельно.

### Уже полученные результаты подготовки

- Токенизатор: Qwen3-Embedding-4B, revision
  `5cf2132abc99cad020ac570b19d031efec650f2b`; audit расположен на GPU в
  `/root/rlt/runs/card-audit/`. Выборка ручного просмотра (40 карточек) хранится
  только там же.
- A/D: 65,473 карточки, 30,617 поставщиков, SHA-256
  `76b564d146be8a04774a58b2b0e3390e30696a31b50ff90ea57cc560972326a6`.
  При лимите 256 обрезается 20.56% карточек и 23.32% токенов; при 512 — 5.49%
  карточек и 5.91% токенов.
- B: 65,473 карточки, те же поставщики; товары стоят перед примерами. При 256
  обрезается 33.13% карточек и 31.26% токенов. Полностью выпадают 18.2% товарных
  фрагментов против 20.3% в A.
- C: 82,444 карточки на тех же поставщиков; максимум 16 карточек на ИНН.
  При 256 обрезается 26.32% карточек и 23.33% токенов; полностью выпадают 14.2%
  товарных фрагментов. Сравнение retrieval ещё должно проверить, оправдывает ли
  больший индекс этот выигрыш по буквальной сохранности названий.
- Подробные метрики по длинам и хеши вариантов зафиксированы в
  [`EXPERIMENTS.md`](EXPERIMENTS.md). Ни одна из этих цифр пока не доказывает
  рост качества поиска.
- Для экономии времени GPU retrieval B и C оставлены за пределами текущей
  серии. Сначала сравниваются A и D: D сохраняет почти весь контекст при том же
  количестве карточек; C увеличивает индекс на 26% и остаётся следующим
  кандидатом, только если D не поможет.
- В mentions-коде добавлена привязка товарного фрагмента к исходному lot ID;
  синтетический тест проверяет эту связь. Следующая генерация audit-артефактов
  запишет provenance в производные mentions parquet; идентификаторы останутся
  на сервере.
