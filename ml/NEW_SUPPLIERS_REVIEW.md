# Экспертная проверка новых поставщиков (D3)

Исторические победители не являются разметкой новых компаний, поэтому новые
поставщики оцениваются отдельной экспертной выборкой. Это малая выборка для
проверки достоверности оснований, а не оценка рынка.

## Набор запросов

`ml/configs/new_suppliers_queries.jsonl` — 33 запроса в 6 категориях
(бумага, кабель и электрика, продукты, текстиль и спецодежда, металлоизделия,
бытовая химия), с однозначными и сложными требованиями (формат, плотность,
ГОСТ, мощность, размеры). Набор зафиксирован до прогона и не меняется по
результатам.

## Порядок

1. На сервере загружен набор ИНН архива: `docker compose run --rm sync-job archive-roster`;
   `GET /api/health/ready` не содержит `novelty` в `degraded`.
2. Лист разметки: `rlt-review-new-suppliers select --queries configs/new_suppliers_queries.jsonl
   --api https://… --out new-suppliers.csv` — до пяти кандидатов `novelty = new` на
   запрос; запросы без новых кандидатов остаются в листе.
3. Для каждого кандидата эксперт заполняет `identity_ok`, `novelty_ok`, `product_ok`,
   `requirements_ok`, `link_ok`, `role_ok` значениями `yes` / `no` / `unknown`,
   метку `label` и краткое обоснование `rationale`:
   - `fits` — подходит: товар соответствует, требования подтверждены, связь с компанией есть;
   - `after_clarification` — возможно после уточнения;
   - `does_not_fit` — не подходит;
   - `insufficient` — недостаточно данных.
4. Спорные случаи по возможности размечает второй эксперт (`reviewer`); при одном
   оценщике это явно указывается в отчёте.
5. Агрегаты: `rlt-review-new-suppliers aggregate --sheet new-suppliers.csv
   --out ml/reports/new-suppliers.json` — доля запросов с хотя бы одним подходящим
   новым поставщиком, распределение меток, ложные подтверждения (система дала
   `recommended`, эксперт — `does_not_fit`/`insufficient`), неработающие доказательства,
   неизвестные поля, число оценщиков.

Все ошибки сохраняются в листе и отчёте; кандидаты из демонстрационной подборки
(E1) берутся только из строк с меткой `fits`.
