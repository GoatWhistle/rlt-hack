# Развёртывание через GitHub Actions

Workflow `.github/workflows/ci-cd.yml` запускается для pull request, push в `main`
и вручную. На PR выполняются проверки и проверка контейнеров. При включённом
`DEPLOY_ENABLED` после успешных проверок `main` образы передаются на сервер
по SSH и запускаются.
Если появился более новый коммит `main`, устаревший выпуск пропускается.

## Проверки

- Frontend: Node.js 24, `npm ci`, `npm run verify`, production-сборка,
  Playwright для desktop/mobile и axe.
- Backend: Python 3.13, Ruff, девять проверок хранилища, джобы и адаптеров
  на искусственных данных, без обращения к внешним каталогам.
- ML: Python 3.12, Ruff и pytest на искусственных данных. GPU-зависимости
  не устанавливаются; GPU-тест пропускается. Датасет LFS не загружается.
- Контейнеры: ShellCheck, сборка frontend/backend, запуск отдельной тестовой БД,
  резервная копия и восстановление тестовой таблицы, миграции и их повторное
  применение, проверка HTTP, ограничения частоты (`429`), непривилегированного
  пользователя API, закрытой документации OpenAPI и отката после заведомо
  неисправного выпуска.
- Зависимости backend: `pip-audit` по `uv export --frozen` из `uv.lock`.

## Сервер

Нужны Linux, Docker, Compose 2.24.4+, Bash, `flock`, OpenSSH и минимум 2 GiB
свободного диска перед загрузкой образов. Рабочая конфигурация — корневой Compose
с наложенным `deploy/compose.production.yml`.

- Пользователь: `rlt-deploy`, член группы Docker.
- Приложение и выпуски: `/opt/rlt-hack/releases/<commit>`.
- Текущий и предыдущий выпуски: `/opt/rlt-hack/current`, `/opt/rlt-hack/previous`.
- Настройки: `/etc/rlt-hack/production.env`, права `root:rlt-deploy`, `0640`.
- Внешние данные для ручного запуска джобы: `/opt/rlt-hack/data`, только чтение.
- Compose-проект: `rlt-hack`; тома БД и резервных копий сохраняются между выпусками.
- Сайт: порт 8081. ClickHouse: только localhost, 18123/19000.
- Веб-интерфейс БД запускается вручную профилем `admin`, только localhost:13488.

Фронтенд обращается к сервису `api`; он поднимается вместе с фронтендом при
каждом выпуске и слушает только localhost:18082.
Обучение ML и автоматический обход внешних источников в деплой не входят.
Сервисы других Compose-проектов и ML-каталог `/root/rlt` не обслуживаются этими
скриптами. HTTPS подключается отдельно после назначения домена.

## Сервер ветки `deploy`

Ветка `deploy` выкатывается только на 51.250.72.225: адрес и ключ SSH сервера
зафиксированы в `deploy/deploy-vm.sh` и `deploy/vm_known_hosts`, подключение к
другому хосту отклоняется проверкой ключа. Сервер подготовлен `bootstrap.sh`,
настройки лежат в `/etc/rlt-hack/production.env`, выпуски — в `/opt/rlt-hack`.

Ручной деплой из чистой рабочей копии на ветке `deploy` (нужен вход `ssh rlt`
с `sudo`): образы собираются на сервере, затем `release.sh` делает резервную
копию БД, миграции и переключение выпуска.

```sh
bash deploy/deploy-vm.sh
```

Автоматический деплой при push в `deploy` выполняет задача `deploy-vm` после
всех проверок CI. Для включения: создать environment `vm` с доступом только из
ветки `deploy`, добавить в него secret `VM_DEPLOY_SSH_KEY` (закрытый ключ,
публичная часть которого с `restrict` записана в
`/var/lib/rlt-deploy/.ssh/authorized_keys`) и variable репозитория
`VM_DEPLOY_ENABLED=true`.

Caddy на сервере обслуживает `rlt.goatwhistle.ru` и пока проксирует его на
прежний сервер. На локальный выпуск (`reverse_proxy 127.0.0.1:8081`) домен
переключается после переноса данных ClickHouse.

## Первичная настройка

Создать отдельный SSH-ключ и передать на сервер его публичную часть,
`bootstrap.sh` и `production.env.example`. Запустить от root:

```sh
bash bootstrap.sh /path/to/deploy_ed25519.pub
```

Скрипт создаёт пользователя и каталоги, добавляет ключ с ограничением `restrict`
и генерирует пароль ClickHouse. При повторном запуске существующий env сохраняется.
Закрытый ключ и пароль в репозиторий не помещаются.

В GitHub создать environment `production`. Variables задать на уровне
репозитория, Secrets — в environment `production`:

| Вид | Имя | Значение |
| --- | --- | --- |
| Variable | `DEPLOY_HOST` | IP или DNS сервера |
| Variable | `DEPLOY_URL` | `https://rlt.goatwhistle.ru` |
| Variable | `DEPLOY_USER` | `rlt-deploy` |
| Variable | `DEPLOY_ENABLED` | `true` после подготовки сервера и секретов |
| Secret | `DEPLOY_SSH_KEY` | Закрытый ключ отдельного пользователя |
| Secret | `DEPLOY_KNOWN_HOSTS` | Проверенная запись публичного ключа SSH сервера |

Доступ к production environment ограничить веткой `main`. SSH-пароль root
workflow не использует. Образы передаются как артефакт Actions с SHA-256,
доступ сервера к приватному GitHub-репозиторию или registry не требуется.
До включения `DEPLOY_ENABLED` выполняется только CI, сервер не обновляется.

Для домена `rlt.goatwhistle.ru` подготовлен отдельный блок `deploy/Caddyfile`.
Его добавляют в существующую конфигурацию Caddy после проверки DNS и готовности
фронтенда на localhost:8081; основной файл сохраняют перед изменением,
проверяют `caddy validate` и применяют через reload. Порт frontend можно
ограничить localhost переменной `WEB_BIND=127.0.0.1`.

При `RLT_RUN_WORKERS=true` деплой также обновляет воркер эмбеддингов. Перед
миграцией он и прежний `parser-worker` останавливаются; после неё
`deploy/run-workers.sh` поднимает только воркер эмбеддингов. Модель должна быть заранее загружена в локальный том.
При сбое скрипт пытается восстановить воркеры предыдущего выпуска, если они
в нём предусмотрены. Подробности — [воркеры и векторизация](WORKERS.md).

## Обновление и откат

Выпуск содержит три образа: `rlt/frontend`, `rlt/backend-api` (API от
непривилегированного пользователя) и `rlt/backend` (миграции, джоба, воркеры).
`release.sh` проверяет хеши и метки ревизии образов, блокирует параллельный деплой,
поднимает ClickHouse и делает синхронный `BACKUP DATABASE` в отдельный том.
Только после успешной копии применяются миграции, затем обновляется frontend.
Ссылка `current` переключается после успешных healthcheck и HTTP-запроса.
Перезапуск frontend и ClickHouse может дать короткий перерыв в доступности.

При сбое обновления frontend скрипт возвращает его предыдущий образ. Ручной откат:

```sh
bash /opt/rlt-hack/current/deploy/rollback.sh
```

Откат приложения не откатывает миграции БД. Перед изменением схемы нужно сохранять
совместимость с предыдущим приложением; восстановление БД из копии выполняется
отдельно после проверки. Имя копии записано в `backup-before.txt` каждого выпуска.
Копии на том же сервере не заменяют внешнее резервное хранение.

Для ручных команд выбрать ревизию и конфигурацию:

```sh
cd /opt/rlt-hack/current
export RLT_IMAGE_TAG="$(basename "$(readlink -f /opt/rlt-hack/current)")"
docker compose --project-name rlt-hack --env-file /etc/rlt-hack/production.env \
  -f docker-compose.yml -f deploy/compose.production.yml ps
```

В этой команде `ps` можно заменить на `logs --tail 100 frontend clickhouse`,
`run --rm sync-job providers` или `--profile admin up -d clickhouse-ui`.
Включение источников и доступ к исходным CSV задаются серверным env.

## Ручной парсинг

Обход источников автоматически не запускается: ни деплой, ни расписание его не
стартуют. Запуск — workflow «Parsing» (`parsing.yml`) в GitHub Actions. Он по
SSH вызывает `deploy/run-parsing.sh`, который стартует один `sync-job sync` в
фоновом контейнере `rlt-hack-parsing` текущего выпуска и сразу возвращает
управление: полный обход ProductCenter идёт часами и не помещается в задание
Actions. Перед запуском скрипт поднимает и ожидает `clickhouse`, потому что
контейнер стартует с `--no-deps` и `depends_on` сервиса не действует. Второй
запуск, пока идёт первый или работает `parser-worker`, отклоняется. Какие
источники обходить, задаёт серверный env.

Ход обхода: `docker logs --follow rlt-hack-parsing`, итоги — в журнале
`crawl_runs` (`run --rm sync-job runs --source <UUID>`). Деплой во время обхода
не останавливает этот контейнер; новый выпуск лучше выкатывать после его
завершения, если меняется схема.

## Реестр МСП ФНС

Роли компаний берутся из реестра МСП, который загружается вручную: в GitHub
Actions запустить workflow «MSP registry import» (`msp-registry.yml`). Поле
`dump_url` можно оставить пустым — тогда скрипт берёт самую свежую выгрузку со
страницы открытых данных ФНС. Новая выгрузка выходит 10-го числа каждого месяца.

Workflow по SSH вызывает `deploy/import-registry.sh` текущего выпуска. Скрипт
скачивает архив около 2 ГБ в `/opt/rlt-hack/msp` параллельными диапазонами
(сервер ФНС ограничивает скорость одного соединения), сверяет размер и
запускает `sync-job registry-import`. Перед импортом скрипт поднимает и ожидает
`clickhouse`: обе джобы запускают контейнер с `--no-deps`, поэтому `depends_on`
сервиса не действует, и на остановленной базе команда падала с
`Connection refused`. Уже скачанная выгрузка повторно не
загружается, а прерванная докачивается. Каталог должен принадлежать
пользователю деплоя; `sync-job` монтирует его только для чтения. Без
загруженного реестра обход источников работает, но роли не проставляет.

Скрипты production не удаляют тома, резервные копии и старые выпуски.
Завершившийся контейнер ручного парсинга сохраняется до следующего запуска:
его код завершения доступен через `docker inspect rlt-hack-parsing`, журнал —
через `docker logs rlt-hack-parsing`. Журнал ограничен тремя файлами по 10 МБ.
Следить за свободным диском и вручную удалять только заведомо ненужные артефакты.
`deploy/smoke.sh` удаляет только собственное временное окружение `rlt-ci-*`.

Источники: [GitHub Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets),
[Compose healthcheck/wait](https://docs.docker.com/reference/cli/docker/compose/up/),
[резервное копирование ClickHouse](https://clickhouse.com/docs/operations/backup).

Для production с внешним совместимым энкодером 4B задайте
`RLT_RUN_LOCAL_EMBEDDER=false` в серверном `production.env`. Тогда
`run-workers.sh` запускает векторизацию без контейнера локального энкодера.
Рабочая модель определяется серверным файлом `EMBEDDING_ENV_FILE`; кеши
локальных энкодеров не требуются.

### Qwen4B на V100

Локальный FP16 runtime: `ml/serving/qwen4b/api.py`, PyTorch 2.6 CUDA 12.4,
Transformers 4.51.3. Требуются рабочие `nvidia-smi` и `python3-venv`.
Подготовка закреплённой ревизии: `sudo bash deploy/prepare-qwen4b.sh <HF-SHA>`.
В `/etc/rlt-hack/qwen4b.env` задайте `QWEN4B_MODEL_DIR`, `QWEN4B_MAX_TOKENS=4096`,
`QWEN4B_BATCH_SIZE=8`. Unit `deploy/qwen4b.service` слушает только Docker gateway
172.18.0.1:11436; при другой подсети измените адрес unit. Веса вне Git;
`HF_HUB_OFFLINE=1`, запросы сверх лимита отклоняются без обрезания.
Перед сменой `EMBEDDING_INFERENCE_URL` выполните
`ml/serving/qwen4b/check_compatibility.py --local-url http://172.18.0.1:11436 --report <server-json>`
в окружении действующего энкодера. Проверка численная, не метрика качества.
Не смешивайте векторы другой модели или несовместимой ревизии под старым ключом.

При включённом историческом поиске `run-workers.sh` идемпотентно импортирует
также полный архив до среза manifest: `src.application.import_procurements`,
батч5000, память DuckDB512MB. В `procurement_archive_imports` фиксируются SHA256,
дата, количества и completed. Иной срез или старые данные без аудита требуют
отдельной миграции; автоматическое смешивание запрещено. При повторе незавершённого
импорта устойчивые ID сохраняют логические количества. Отображаемые примеры
выбираются из полного архива после completed; это не текущие предложения.

Для ускорения исторического поиска на V100 задайте локальному unit
`QWEN4B_PROFILE_INDEX_DIR=/opt/rlt-hack/data/supplier-index/<active-index>`
и backend `PROFILE_SIMILARITY_URL=http://172.18.0.1:11436`.
Runtime проверяет Qwen4B, форму и SHA256 матрицы, держит нормализованный
float32 кеш на GPU. ClickHouse остаётся хранилищем; индекс и порядок карточек
совпадают с manifest. При заданном адресе ошибка сервиса не скрывается;
без адреса остаётся прежний поиск ClickHouse. `CLICKHOUSE_CPUS` задаёт квоту БД.
